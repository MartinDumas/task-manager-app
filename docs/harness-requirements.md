# Harness Requirements — Task Manager API

**Ідентифікатор:** HAR-REQ-01  
**Практична робота:** № 1  
**Стан:** початкова специфікація (компоненти будуть реалізовані на наступних практичних)  
**Дата:** 25.10.2026

## 1. Мета та межі

Agent harness — інженерна інфраструктура, яка керовано допомагає розробляти застосунок Task Manager API. Він не є функцією самого менеджера завдань: забезпечує джерела даних, базу знань, відтворювані skills, guardrails, координацію ролей і оцінювання роботи агента. Архітектурні рішення та прийняття змін залишаються за студентом.

## 3. Knowledge layer та правила доступу

- Репозиторій `task-manager-vault` фізично окремий від `task-manager-app`; формат майбутніх знань — Markdown із YAML frontmatter та wiki-посиланнями Obsidian.
- На ПР1 репозиторій vault порожній. У ПР2 створюються нотатки й зв'язки; у ПР3 реалізується MCP-сервер для ingestion і retrieval.
- MCP-сервер запускається як окремий контрольований процес і отримує налаштовані шляхи до локальних клонів. Агент не повинен мати прямого файлового доступу до vault; передбачити sandbox/ACL та hook-політики поряд з MCP-інструментами.
- Базові плановані MCP-операції: `kb_search(query)` — читання релевантних нотаток; `kb_get_note(id)` — читання конкретної нотатки; `kb_ingest(source, content, metadata)` — контрольоване оновлення vault. Точний контракт визначатиметься у ПР3.
- Кожна нотатка повинна вказувати джерело, час оновлення та тип знання (вимога, рішення, компонент, тест); не розміщувати в нотатках токени або приватні дані.

## 4. Цільові автономні задачі (3–5)

### AT-01. Генерація каркасу модулів

За затвердженою архітектурою агент створює шаблони endpoint/service/repository/schema і базові перевірки. Це скорочує повторювану роботу, але зміни коду потребують перегляду.

### AT-02. Генерація тестів

Для змінених endpoint-ів агент готує pytest-тести на успішні та помилкові сценарії. Це прискорює регресійний контроль і дає вимірюваний результат.

### AT-03. Рев’ю коду

Агент перевіряє новий код на відповідність вимогам, поділ відповідальності, валідацію та відсутність секретів. Результат — перелік зауважень, а не автоматичне схвалення.

### AT-04. Синхронізація документації

На основі перевірених змін агент пропонує оновлення описів API, ADR і нотаток у knowledge layer через MCP. Це зменшує розбіжності між кодом і знаннями.

### AT-05. Аналіз помилок тестування

Агент читає вихід pytest/Ruff і зіставляє помилки з кодом та рішеннями із vault через MCP; пропонує обмежений патч для ручного затвердження.

## 5. Первинні guardrails

| Реакція | Категорії дій | Пояснення |
|---|---|---|
| Allow | Читання вимог, коду, тестів і diff; побудова плану; запуск безпечних read-only перевірок | Низький ризик, відсутність зміни стану. |
| Warn / Require approval | Редагування коду чи документації; встановлення залежностей; commit; міграція схеми; інжестія нотаток до vault через MCP | Потрібне явне підтвердження користувача перед зміною. |
| Block | rm -rf даних; git reset --hard або force push; push до захищеної гілки; читання/запис vault повз MCP; експорт секретів; виробничі операції | Неприпустимі втрати, обхід межі доступу або витік інформації. |

**Принцип контролю:** політика в документації сама по собі не блокує shell-команди. На ПР4 передбачити перевірені hooks, deny/approval-правила, обмеження доступу до файлової системи, негативні тести обходу. У разі невпевненості — запит підтвердження.

## 6. Обрана IDE та план реалізації шарів

- **JetBrains WebStorm + плагін GitHub Copilot (Agent); для hooks — Copilot CLI у терміналі WebStorm.** Підключення MCP, термінальні інструменти з дозволами, `.github/copilot-instructions.md`, skills (Preview), custom agents. Вбудовані hooks для JetBrains наразі не гарантуються поточною таблицею сумісності GitHub, тому їхню реалізацію та перевірку через CLI віднесено до ПР4.
- ПР1: вимоги й структура репозиторіїв.
- ПР2: knowledge layer в Obsidian vault.
- ПР3: ingestion / retrieval через MCP-сервер.
- ПР4: guardrails та hooks.
- ПР5: повторно застосовні skills.
- ПР6: orchestration / custom agents.
- ПР7: evaluation, RAG та порівняння з/без harness згідно з умовами роботи.

## 7. Принцип оцінювання

- **Task success rate:** успішно завершені задачі / всі задачі з фіксованого набору.
- **Guardrail violations:** кількість реально виконаних заборонених операцій (ціль — 0).
- **Knowledge correctness:** частка відповідей про вимоги/архітектуру, підтверджених актуальними нотатками, а не домислами.
- **Time/effort:** тривалість і кількість ручних виправлень на однакових задачах з harness та без нього.
- ПР1 визначає показники, але не заявляє про досягнуті значення: вимірювання заплановані для ПР7.

## 8. Умови готовності harness

Агент використовує вимоги як джерело істини, не обходить MCP до vault, дотримується дозволів, формує відтворювані зміни з тестами, а результати можна перевірити за наперед визначеними метриками.
