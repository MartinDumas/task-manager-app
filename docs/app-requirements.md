# Вимоги до застосунку «Менеджер завдань»

**Ідентифікатор документа:** APP-REQ-01  
**Практична робота:** № 1  
**Статус:** базова версія вимог (план, не реалізація)  
**Дата:** 25.10.2026

## 1. Призначення та межі

Task Manager API — невеликий однокористувацький локальний сервіс керування персональними завданнями. Надає HTTP API та автоматичну інтерактивну документацію OpenAPI (Swagger UI). Цільовий користувач — студент або окремий користувач, який планує власні справи. Продукт створюється з нуля протягом семестру та служить тестовим об'єктом для agent harness.

**У межах:** CRUD завдань, статуси, пріоритети, дедлайни, пошук, фільтри, статистика.  
**Поза межами:** реєстрація й автентифікація, командні простори, e-mail/Telegram-сповіщення, платіжні сервіси, хмарний production-деплой, повноцінний frontend.  
**Роль:** один локальний користувач; база містить лише навчальні/демонстраційні дані.

## 2. Предметна модель

**Task:** `id` (ціле додатне, PK), `title` (рядок 1–120), `description` (рядок 0–2000, nullable), `status` (todo, in_progress, done), `priority` (low, medium, high), `due_date` (ISO 8601 date, nullable), `created_at` (UTC datetime), `updated_at` (UTC datetime). Після створення `status=todo`, `priority=medium`, якщо не передано інше.

## 3. Функціональні вимоги

| Код | Функція | Опис | Критерій приймання |
|---|---|---|---|
| FR-01 | Створення завдання | Користувач створює завдання з обов’язковою назвою (1–120 символів), необов’язковим описом (до 2000 символів), пріоритетом та строком виконання. Початковий статус — todo. | POST /api/v1/tasks; 201 Created, повертається id. |
| FR-02 | Перегляд завдання | Користувач отримує повні дані завдання за унікальним ідентифікатором. | GET /api/v1/tasks/{id}; 200 або 404. |
| FR-03 | Список завдань | Користувач переглядає список завдань із пагінацією (limit 1–100, offset ≥ 0). | GET /api/v1/tasks; список і кількість записів. |
| FR-04 | Редагування | Користувач може змінити назву, опис, пріоритет і строк виконання наявного завдання. | PATCH /api/v1/tasks/{id}; валідація даних. |
| FR-05 | Керування статусом | Користувач змінює стан завдання між todo, in_progress і done; у відповіді відображено актуальний стан. | PATCH /api/v1/tasks/{id}/status. |
| FR-06 | Видалення завдання | Користувач видаляє вибране завдання після явного запиту; після видалення воно недоступне. | DELETE /api/v1/tasks/{id}; 204 або 404. |
| FR-07 | Пошук | Користувач шукає завдання за фрагментом назви або опису без урахування регістру. | GET /api/v1/tasks?q=...; збіги у двох полях. |
| FR-08 | Фільтрація й сортування | Користувач фільтрує за статусом і пріоритетом, сортує за created_at або due_date у висхідному чи спадному порядку. | GET /api/v1/tasks?status=...&priority=...&sort_by=... |
| FR-09 | Статистика | Користувач отримує кількість усіх завдань та кількості за кожним статусом. | GET /api/v1/tasks/stats; total = сума станів. |

| NFR-03 | Безпека | Навчальний однокористувацький прототип використовується локально; секрети не зберігаються у Git; SQL-запити формує ORM, а доступ до БД не надається напряму агенту. | Перевірка репозиторію й негативні тести введення. |
| NFR-04 | Надійність | Операції збереження атомарні; некоректні запити повертають 4xx; неочікувані помилки не розкривають внутрішні дані. | Тести валідації, транзакцій, обробки помилок. |

## 5. Технологічний стек і архітектура

- Python 3.12+; FastAPI (REST/OpenAPI), Pydantic (валідація), SQLAlchemy 2.x (ORM), SQLite (локальна БД).
- pytest і pytest-cov (автоматизовані перевірки), Ruff (статичний аналіз), Git (версіювання).
- Шари: HTTP API → services (бізнес-правила) → repositories (доступ до даних) → SQLite. Схеми запитів/відповідей відокремлено від ORM-моделей.
- Усі маршрути починаються з `/api/v1/`; Swagger UI на `/docs`.
- Код застосунку не містить логіки agent harness. Обидва розвиваються паралельно в репозиторії застосунку; vault фізично окремий.

## 6. Погоджені рішення та припущення

1. Вибрано локальний API без окремого графічного frontend, щоб укластися у сім практичних робіт.
2. Автентифікація не реалізується: API призначено лише для локального навчального використання; публічно виставляти сервіс не можна.
3. Дата і час створення/зміни зберігаються в UTC; `due_date` зберігається як дата без часу.
4. Усі наведені порогові показники — критерії майбутнього приймання, а не вже отримані вимірювання.

## 7. Обрана агентна IDE

**JetBrains WebStorm + GitHub Copilot (плагін із режимом Agent; для hooks — Copilot CLI у терміналі WebStorm).** Плагін підтримує MCP-сервери, роботу з файлами та командами з підтвердженням користувача, репозиторні інструкції, custom agents і skills (для JetBrains — Preview). Вимоги та правила фіксуються в `.github/copilot-instructions.md`; подальші skills — у `.github/skills/`, а агенти — у `.github/agents/`. Налаштування MCP залежить від версії плагіна. За актуальною таблицею сумісності GitHub, hooks не підтримуються безпосередньо для JetBrains IDE, тому у практичній роботі № 4 передбачається застосувати GitHub Copilot CLI через вбудований термінал або альтернативну сумісну оболонку запуску, перевіривши фактичне блокування небезпечних дій. Стек Python/FastAPI запускається в терміналі WebStorm, без вимоги до повного Python IDE-плагіна.

Робочий простір IDE — **лише репозиторій застосунку**. Доступ до vault має відбуватися виключно через контрольований MCP-сервер із власними правами. Одного лише відкритого workspace недостатньо для захисту від довільної shell-команди: додаткові обмеження мають забезпечувати дозволи інструментів і середовища.

## 8. Визначення готовності продукту

Наприкінці курсу всі FR-01…FR-09 мають проходити API-тести; виконуються NFR-01…NFR-06; документація і база знань узгоджені з реалізацією. На ПР1 реалізацію цих вимог лише заплановано.
